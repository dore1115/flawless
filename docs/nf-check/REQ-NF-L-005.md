# REQ-NF-L-005 로그인 응답 지연 측정

- 확인일시: 2026-09-17
- 확인자: 김유하
- 확인 환경: docker (erp-app), k6 부하테스트 도구 (container/k6/login-load-test.js)
- 기준: 동시 사용자 100명, 평균 응답 500ms 초과 또는 p95 1초 초과 시 결함

## 확인 방법
1. 기존 container/k6/load-test.js(근태 조회 API 대상)를 참고하여
   로그인(/login) 전용 스크립트 login-load-test.js 신규 작성
2. 시나리오: 30초간 20명 → 1분간 50명 → 1분간 100명 → 30초 쿨다운 (총 3분)
3. 스프링 시큐리티 CSRF 보호로 인해 최초 curl 테스트에서 403 발생 확인
   → 로그인 페이지(GET /login)에서 CSRF 토큰을 먼저 획득한 뒤
   로그인 요청에 포함하도록 스크립트 수정
4. k6 run container/k6/login-load-test.js 실행

## 판단
- 동시 사용자 100명 기준, p95 응답시간 약 50ms로 기준치(1초) 대비 매우 양호.

  → 2026-09-25 스크립트 보완 후 재측정한 결과(아래)를 개선 전 기준값으로 사용함.

## 비고
- 최초 테스트 스크립트는 CSRF 토큰 없이 로그인 요청을 보내 100% 실패(403)했음.
  이는 성능 문제가 아니라 스프링 시큐리티의 CSRF 방어가 정상 작동한 것으로,
  스크립트를 CSRF 토큰 포함 방식으로 수정 후 재측정함.

# REQ-NF-L-005 개선 전 재측정 (스크립트 보완)

- 확인일시: 2026-09-25
- 확인자: 김유하
- 확인 환경: docker (erp-app, erp-mysql), k6 (container/k6/login-load-test.js)

## 재측정 배경
- 기존 스크립트는 응답코드(302)만 확인하여, 로그인 실패(302 → /login)도 성공으로 집계되는 문제가 있었음.
- 실제로 L-001 검증 때 DB 비밀번호를 해시로 바꿔 둔 상태여서, 평문 비교 코드인 본 브랜치에서 로그인이 전부 실패하고 있었음.
  (09-25 1차 측정값 p95 18.75ms는 실패한 로그인 기준이므로 무효 처리)
- DB 비밀번호를 seed 상태(평문)로 되돌린 뒤, 스크립트를 아래와 같이 보완하여 재측정함.

## 스크립트 보완 내용
- 로그인 성공 여부 확인 추가 (302이면서 /login으로 돌아가지 않을 때만 성공)
- 로그인 요청(POST /login) 시간만 따로 측정 (login_duration)
- 가상 사용자마다 다른 계정 사용 (emp001 ~ emp100)

## 결과
| 항목 | 결과 | 기준 |
|---|---|---|
| 로그인 성공률 | 100% (7,930건) | - |
| 평균 로그인 시간 | 16.88ms | 500ms 이하 |
| p95 로그인 시간 | 96.99ms | 1000ms 이하 |

## 판단
- 결함 코드(Employee의 department/position EAGER 로딩)는 존재함.
- 다만 사원 100명 규모에서는 기준치를 넘는 지연은 발생하지 않음.
- → 이 수치를 L-005 **개선 전 기준값**으로 사용하고, 개선 후 동일 조건으로 재측정하여 비교함.

## 최종 결론
- 로그인 성공을 검증한 상태로 동시 사용자 100명 측정 결과, 평균 16.88ms / p95 96.99ms로 기준(평균 500ms, p95 1초)을 충족함.
- EAGER 로딩 결함 코드는 존재하나, 현재 데이터 규모에서는 성능 기준에 영향을 주지 않으므로 개선 불필요로 판단함.
- 개선 시에는 Employee 엔티티(공용)를 수정하지 않고, 로그인 전용 조회(아이디/비밀번호/권한만 조회)를 추가하는 방식을 권장함.
- → **REQ-NF-L-005 결함 미해당 (실측 기준 충족)**
